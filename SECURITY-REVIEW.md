# Security review — Simulant Better-Auth setup

**Date:** 2026-05-06
**Scope:** simulant-auth library, login.simulant.shop deployment, all
consumer apps that read sessions, the cross-subdomain cookie model.

This is a self-audit, not a third-party assessment. Things to take to a
real penetration test before relying on the system at scale.

---

## TL;DR

Setup is sound for a 5000-user education product. Critical defaults
(HttpOnly, Secure, SameSite=Lax, password hashing, signed sessions)
are correct. The risks worth fixing soon are:

1. **No request rate limiting** — any single attacker can pound
   `/sign-in/email` with credential-stuffing attempts. Better-Auth's
   built-in rate limiter is **not enabled**. Easy fix.
2. **No CAPTCHA / bot detection** — same vector. Sentinel plugin from
   Better-Auth is the standard answer; not enabled.
3. **No DMARC / DKIM verification** documented — login emails go via
   smtp2go. If your sender domain `simulant.shop` doesn't have DMARC
   record set to `p=quarantine` or `p=reject`, attackers can spoof
   "From: noreply@simulant.shop" and phish your users for password
   resets. Cheap to fix at the DNS layer.
4. **Cookie path is `/`** which is fine, but `__Secure-` prefix would
   add belt-and-suspenders for the cookie hijack scenario.
5. **No 2FA enforced for superadmins** — superadmin status grants
   ecosystem-wide access; recommend forcing 2FA for that role at
   minimum.

Everything else flagged below is informational.

## 1. Cryptography & secrets

### 1.1 Cookie signing
- **Algorithm:** Better-Auth uses HMAC-SHA256 over the session token
  with `BETTER_AUTH_SECRET`. Standard. Not user-configurable in 1.6.x.
- **Key entropy:** `MUvQoxeyE9+pk/bHFLcQBnIUEP6kFfDOypD9YF+0dzo=` —
  32 bytes from `openssl rand -base64 32`. ~256 bits. ✅
- **Key distribution:** same secret on every app. Required for
  cross-subdomain cookie validation. Each app holds the secret in its
  Coolify env. **Risk:** if any one app leaks env to a third party,
  the attacker can forge cookies for *every* app. Mitigation: rotate
  by re-running `openssl rand -base64 32` and updating all 12 Coolify
  apps simultaneously (everyone gets logged out — accept the friction
  in exchange for the security). No rotation cadence is currently set.
- **Recommendation:** **annual rotation** at minimum. Calendar reminder
  in your runbook.

### 1.2 Password hashing
- **Algorithm:** Better-Auth uses scrypt by default (1.6.x). Memory-hard,
  OWASP-approved for new deployments. ✅
- **Salt:** per-row, generated at hash time. ✅
- **Plaintext storage anywhere:** none. The `password` column on
  `account` holds only the scrypt hash. Plaintext is ephemeral —
  hashed in-process and discarded. ✅
- **Migrated users:** all 69 users imported from Stack have `password
  = NULL`. Sign-in attempts will fail until the user resets via the
  forgot-password flow. **This is correct** — never accepted Stack's
  hash, never ran an unsafe migration.

### 1.3 Reset / verification tokens
- **Storage:** `verification` table. Tokens are random 32+ char strings
  generated by Better-Auth (cryptographically random, not predictable).
- **Hashed?** Stored as **plaintext** in the `verification` table. If
  the auth DB is exfiltrated, an attacker with read access could use
  any unexpired token to reset a user's password. **Risk: medium.**
  Mitigation: ensure libsql/sqld access is locked down (see §3).
  Better-Auth doesn't currently support hashed verification tokens
  (open issue upstream).
- **Expiry:** 1 hour default. ✅

### 1.4 JWT (oauth-provider plugin)
- **Algorithm:** ES256 (asymmetric). Public key served at `/api/auth/jwks`.
- **Key rotation:** Better-Auth's jwt plugin rotates keys automatically.
  Old key kept for verifying outstanding tokens until expiry. ✅
- **Audience / issuer:** derived from `BETTER_AUTH_URL`. If you ever
  serve from a different host, update this env. ✅

## 2. Session & cookie security

### 2.1 Cookie attributes
Set on `.simulant.shop`:

| Attribute | Value | Notes |
|---|---|---|
| `HttpOnly` | true | XSS can't read the cookie. ✅ |
| `Secure` | true | HTTP transmission rejected. ✅ |
| `SameSite` | Lax | Form POSTs from third-party origins won't include the cookie except top-level GETs. ✅ for normal use. **Not** strict — if you need CSRF protection on state-changing GET requests (you shouldn't, but Next.js might), strengthen to `Strict`. |
| `Domain` | `.simulant.shop` | Cross-subdomain. Required for the federated model. ✅ |
| `Path` | `/` | All apps. ✅ |
| Cookie name prefix | none | Better-Auth uses bare names. **Recommend** `__Secure-` prefix to enforce Secure/HTTPS at the browser. Need to check if Better-Auth supports it. |

### 2.2 Session lifecycle
- **Default expiry:** 7 days. Acceptable.
- **Refresh on activity:** sessions get `updatedAt` bumped on each request.
- **Revocation on password reset:** `revokeSessionsOnPasswordReset: true` ✅
  — when a user resets their password, all their active sessions die.
- **Revocation on sign-out:** server-side row deleted ✅
- **Concurrent sessions:** allowed; users can be logged in on multiple
  devices. Not currently capped. Acceptable.
- **Idle timeout:** none. Sessions only expire on absolute TTL (7 days).
  Consider 30-day idle timeout if you want stronger inactive-session
  hygiene.

### 2.3 CSRF
- **Mechanism:** Better-Auth checks `Origin` and `Referer` headers
  against `trustedOrigins`. Mismatched = rejected. ✅
- **trustedOrigins list:** all 10 Simulant subdomains hardcoded in
  `auth.ts`. Looks correct. Matches the cookie domain.
- **Adding new apps:** add the new domain to trustedOrigins in
  `simulant-auth/src/auth.ts` and redeploy login.simulant.shop. Easy
  to forget — document in README.

### 2.4 Cross-subdomain cookie blast radius
- All 12 apps share the same cookie. **If any one app has an XSS
  vulnerability**, an attacker who exploits it can `document.cookie =
  ""`-set or hijack the session for the user across the entire
  ecosystem.
- HttpOnly mitigates direct cookie theft. But in-page JS could still
  call authenticated endpoints from the user's session.
- **Recommendation:** keep frontend dependency hygiene tight. Audit
  for XSS in `dangerouslySetInnerHTML` across all apps.

```bash
grep -rn "dangerouslySetInnerHTML" --include="*.tsx" simulant-* | grep -v node_modules
```

## 3. Database security

### 3.1 libsql / sqld access
- **DB:** self-hosted sqld on Coolify at `simulant-auth-db.database.bullma.de`.
- **Auth:** bearer token (`SIMULANT_AUTH_DB_TOKEN`). Expires in
  ~year 2126 per the JWT we generated. Effectively never expires.
- **Token in env on every consuming app** — broad exposure. If any
  app's env leaks, the attacker has direct DB read/write.
- **Blast radius:** the DB has every Simulant user's hashed password +
  email + session tokens. Owning this DB = owning the entire
  ecosystem.
- **Network exposure:** is the libsql endpoint exposed to the public
  internet, or only to the Coolify host's internal network? If public,
  Coolify's reverse proxy + the bearer token are the only barriers.
  Ideally, expose only on the Coolify private network.

**Recommendations:**

1. **Lock down the libsql endpoint** to Coolify's internal network only,
   so attackers must first compromise a Coolify-deployed app to reach
   the DB.
2. **Issue a DB token with shorter TTL** (90 days, automated rotation)
   instead of the year-2126 token currently in use.
3. **Log failed DB auth** at the sqld layer so brute-force attempts are
   visible.

### 3.2 Schema integrity
- **Foreign keys:** Better-Auth's schema uses FK references on
  `account.userId`, `session.userId`, `member.userId`,
  `member.organizationId`, `invitation.organizationId` etc. ✅
- **Cascade deletes:** ON DELETE CASCADE on user→account, user→session.
  Deleting a user cleans up correctly.
- **Indexes:** present on user.email (unique), session.token (unique),
  member.organizationId, member.userId. Adequate.

### 3.3 PII data
The auth DB contains:
- email, name, image (URL), createdAt
- password hash (scrypt), session tokens (random)
- organization name, slug, metadata (JSON — may contain CVR, sender
  address, etc. depending on consumer-app usage)
- member roles

**GDPR considerations:**
- Right to erasure: `DELETE FROM user WHERE id = ?` cascades cleanly. ✅
- Right to access: schema is portable; export per-user data is one query.
- Data residency: DB hosted at `bullma.de` (your own infrastructure).
  If schools require EU residency, confirm Coolify host is EU-based. ✅
  (we assumed Frankfurt earlier — verify in your Coolify dashboard).

## 4. Authentication flows

### 4.1 Email + password
- Sign-in endpoint: `POST /api/auth/sign-in/email`
- Validates: email + password against scrypt hash
- Failure mode: returns 401 + generic "Invalid email or password"
- **Rate limited?** Better-Auth's built-in `rateLimit` config is
  **not currently enabled** in `auth.ts`. **Risk: HIGH for credential
  stuffing.**
- **Fix:** add to `auth.ts`:
  ```ts
  rateLimit: {
    enabled: true,
    window: 60,            // seconds
    max: 10,               // requests per window per IP
    customRules: {
      "/sign-in/email": { window: 60, max: 5 },
      "/forget-password": { window: 60 * 60, max: 3 },
    },
  },
  ```

### 4.2 Magic-link, email-OTP
- Both delivered via smtp2go.
- Same expiry 10 minutes.
- **Risk:** attacker enumerates email addresses by submitting random
  emails — error messages should not reveal "user does not exist".
  Better-Auth handles this by default (returns same response
  regardless). ✅

### 4.3 Passkey (WebAuthn)
- RP ID: `simulant.shop` (apex). ✅ allows credentials to roam across
  subdomains.
- Origin check: validated against trustedOrigins. ✅
- Storage: passkey table stores credential metadata (publicKey,
  counter, transports). No private key on the server. ✅
- **Risk:** low; passkey is the strongest factor.

### 4.4 Sign-up
- **Disabled:** `disableSignUp: true` ✅
- Users can only be created by superadmins via console (admin plugin's
  `createUser`) or by the demo signup orchestrator (server-side).
- Public POST to `/sign-up/email` returns rejection. ✅

### 4.5 Forgot password
- Generates a single-use token, stored in `verification` table (1h TTL),
  emailed via smtp2go.
- `revokeSessionsOnPasswordReset: true` — all active sessions die after
  reset. ✅
- **Risk:** anyone can fire `/forget-password` with any email and emit
  a reset email. Without rate limiting, this could be used for
  email-spam DoS against users. See §4.1 fix.

## 5. Authorization (org plugin)

### 5.1 Roles
4-role accessControl matrix:
- `superadmin` — global access (membership in `SIMULANT_ADMIN_TEAM_ID`)
- `workspace_admin` — admin of one school
- `student_manager` — limited admin (invite + read)
- `student` — read-only

Role checks on server side only. Client cannot tamper. ✅

### 5.2 Permission enforcement
- Each consumer app calls `requireUser()` server-side, then checks
  `member.role` for the active org.
- Same enforcement on the auth admin endpoints (banUser, createUser,
  impersonateUser). Better-Auth's admin plugin restricts via
  `adminRoles: ["admin"]`.
- **Gap:** `superadmin` role lives at the org level, but `admin` in
  Better-Auth's admin plugin is a separate user-level role. Currently
  these are not aligned — `auth.api.banUser()` requires user.role ===
  "admin", but our roles are org-level. Verify by trying to ban a user
  from console as the global superadmin. If 403, we need to either
  set user.role on superadmin members OR override the adminRoles list.

### 5.3 Impersonation
- Plugin: `admin().impersonateUser({ userId })` — admin only.
- Audit: every impersonate fires an event. We log to `consoleAudit`
  table on stop with duration.
- **Risk:** impersonation leaves an audit trail in the auth DB
  (session row with `impersonatedBy` field). Verifiable post-hoc.

## 6. Email security

### 6.1 SMTP transport
- smtp2go EU, port 587, STARTTLS.
- Credentials in env: `SMTP_USER`, `SMTP_PASS`. In Coolify only on
  login.simulant.shop (consumer apps don't send email).
- **Recommendation:** add an SMTP-rate-limit on smtp2go's side (per
  account) to cap email blast in case of abuse.

### 6.2 SPF / DKIM / DMARC
**Not verified by this review.** Required for trustworthy delivery.
Run:

```bash
dig TXT simulant.shop
dig TXT _dmarc.simulant.shop
dig TXT s1._domainkey.simulant.shop  # smtp2go's selector
```

Should see:
- SPF: `v=spf1 include:spf.smtp2go.com ~all` (or strict `-all`)
- DMARC: `v=DMARC1; p=quarantine; rua=mailto:...` (start with
  quarantine, escalate to reject when delivery is solid)
- DKIM: smtp2go-issued public key

**Without these, password-reset emails go to spam (UX bug) or get
spoofable (security bug).**

### 6.3 Email content
- Reset emails contain `?token=...` URLs to `login.simulant.shop`.
- Tokens are sufficiently random.
- HTML is hand-rolled in `simulant-auth/src/email.ts` — no template
  injection risk; we only interpolate user.name (escaped via
  `escapeHtml`). ✅

## 7. Network security (WAF / DDoS)

### 7.1 Pre-Better-Auth: Stack hosted everything behind their CDN/WAF.
### 7.2 Post-Better-Auth: every request hits your Coolify host directly.

**Recommendation:** put Cloudflare (free tier is fine) in front of:
- login.simulant.shop
- console.simulant.shop
- All consumer subdomains

Cloudflare provides:
- DDoS protection
- Bot detection (heuristic)
- Rate limiting at the edge (different from Better-Auth's app-layer
  one — defends infrastructure, not just the auth API)
- WAF rules for OWASP top 10
- Geographic blocking (block all traffic outside DK/SE/NO/DE if you
  want a cheap reduction in attack surface)

Setup: add Cloudflare nameservers to your registrar, point all
subdomains to your Coolify origin. Coolify keeps doing TLS termination,
Cloudflare does TLS at its edge as well — you can run "Full (strict)"
mode where both ends have valid certs.

## 8. Operational hygiene

### 8.1 Dependency updates
- Better-Auth security advisories: subscribe at
  https://github.com/better-auth/better-auth/security/advisories.
- npm audit per app: not currently automated.
- **Recommendation:** add Dependabot (GitHub native) to each repo with
  weekly checks. Auto-PR for security patches; manual merge.

### 8.2 Logs
- Better-Auth doesn't ship structured audit logs by default. Sign-ins,
  sign-outs, password resets are not logged automatically.
- We log impersonation in `consoleAudit`. Other auth events are not
  surfaced.
- **Recommendation:** enable Better-Auth's `hooks.after` to log every
  `/sign-in/email` / `/sign-up` / `/forget-password` to `consoleAudit`
  with IP + user-agent. ~20 lines of code.

### 8.3 Backup
- Auth DB backup strategy: depends on your sqld/Coolify config.
- **Verify** that backups are:
  - Off-site (different host than the Coolify primary)
  - Encrypted at rest
  - Regularly tested for restore (every quarter)
- This DB is the single most valuable artifact in the ecosystem. Lose
  it, lose every user account.

### 8.4 Incident response
- No documented runbook for "auth DB compromised" or "BETTER_AUTH_SECRET
  leaked".
- **Recommendation:** write one. Roughly:
  1. Rotate `BETTER_AUTH_SECRET` (everyone gets logged out — that's
     the point)
  2. Force password reset for all users
  3. Audit DB for unexpected `account` or `member` rows
  4. Notify users if PII was exposed (GDPR Article 33 — 72 hours)

## 9. Open questions to validate

1. **Is BETTER_AUTH_SECRET the same on every app?** Confirm by
   diffing the value across Coolify's per-app env. If divergent, only
   one app accepts cookies that another sets — silent breakage that
   looks like "user logged out of half the apps".

2. **Is `SIMULANT_AUTH_DB_URL` reachable only via the Coolify private
   network?** If `curl https://simulant-auth-db.database.bullma.de`
   from a random AWS EC2 returns anything but a connection refused,
   it's exposed.

3. **Have password resets gone out without spam-folder issues?** Test
   by resetting a personal Gmail and a personal Outlook. If any go to
   spam, fix DMARC/DKIM before relying on this for user onboarding.

4. **Is OAuth provider plugin actively used?** It's enabled but only
   the PrestaShop module would use it (and that migration is deferred).
   If no one is using it, **disable the plugin** to reduce attack
   surface.

5. **Are passkeys actively used?** Same question. Disable if not in
   real use — every plugin enabled is a code path that could have
   bugs.
